## 实测节约时间与部署结果

2026-09-14 测试服同一默认 30 天接口，使用同样的服务器本机 HTTP 验证脚本，连续三次：

| 版本 | 第一次 | 第二次 | 第三次 | 平均 |
| --- | ---: | ---: | ---: | ---: |
| 旧版 | 3,874 ms | 3,612 ms | 3,291 ms | 3,592.3 ms |
| 新版（已有预计算结果） | 152 ms | 51 ms | 50 ms | 84.3 ms |

每次平均减少 **3,508 ms，约 97.7%**，约 **42.6 倍**响应速度。100 次同类请求累计减少约 **5 分 51 秒**等待。测量包含获取和解析 JSON，不包含用户公网延迟与浏览器绘制；不是完整页面可交互时间。旧版与新版顺序测量，定时同步可能在期间继续运行。

正式服修复前曾测得约 12.49 秒服务端计算耗时；本次没有发布正式服，不能宣称正式服已达到测试服速度。

排行榜入口和内容已临时关闭，保留实现以便恢复，未删除数据或改变计分。测试服最终 production build、HTTP 五范围、认证隔离、JavaScript 静态资源、周报、核算、单视频详情全部通过。meedoo.service 与 meedoo-sync.timer 均 active。

部署备份：`/opt/meedoo/.deploy-backups/performance-before-20260914T045129Z`。首次测试部署曾因复制时解引用依赖符号链接导致 500，已自动回滚；修正依赖链接解析并验证后再次部署成功。

## 已修复并验证

- Dashboard 历史 SQL 不再对每条指标快照执行一次粉丝归因 SUM / JOIN。改为一次读取归因记录，按视频构建累计值并二分查找历史时间点。
- 单视频详情复用同一实现，并移除分组时反复复制整个数组的做法。
- 保留 PostgreSQL 微秒精度，以及 SQL SUM 的 null / 0 区别。未改变 96 小时归因规则、计分或核算公式。
- 每轮同步完成后，预计算 1 / 7 / 30 / 90 / 365 天看板，结果持久保存在 maintenance_state 的 dashboard:v1:* 项中；页面直接读取对应结果。
- 全部范围计算成功后才在事务内发布；失败保留上一版。过期数据可以先显示，再在响应后刷新。界面更新时间来自缓存生成时间。
- 审批、移除、重试和发布状态变化会使缓存失效。移除/审批与失效在同一事务中；版本校验防止后台旧结果覆盖移除后的数据。
- 冷启动同一时间范围的并发请求共享一次计算；非 UI 的自定义天数保留即时计算，不无限增加缓存项。

### 验证方法

测试服 production build 与 TypeScript 检查；在同一个 repeatable-read 数据库事务内对比旧实现与新实现，覆盖五个范围以及单视频详情，完整响应数值一致。缓存测试覆盖十个并发冷请求、命中不查历史表、五范围预计算、刷新失败保留旧数据、失效重算。测试写入均回滚。

回归脚本：`scripts/verify-analytics-performance.cjs`。运行时需指定旧版本源代码目录，且应只在测试环境运行。HTTP 验证还覆盖未登录请求 401、五范围 200、看板 JavaScript 资源、登录状态、周报、核算和视频详情。

注意：测试库约 3,118 条指标快照，正式库此前约 37,224 条。测试耗时不能直接当作正式服升级后的实测结果。正式服此次未修改。

## 初次审查发现的问题

以下为修复前记录。后续修复及验证见 [可靠性修复记录](reliability-release-2026-09-14.md)。

### 1. P1：同步范围固定，部分视频可能永远不更新

位置：`lib/upload-post-sync.ts` 的 `syncAnalytics()`（约 111 行）；`scripts/import-organic-history.mjs` 的 `applyDatabase()`。

常规同步只选 `p.request_id IS NOT NULL`，并按视频 UUID 排序后 `LIMIT 50`。历史导入把 request_id 写为 NULL，因此这些视频只有导入时的指标，后续常规同步不会更新。超过 50 组发布任务时，也没有分页或轮换，后面的任务可能长期不被选中。

建议：按 platform_post_id 覆盖历史视频，并按最久未同步时间调度或完整分页；给整轮任务设置时间预算和合理并发。

### 2. P1：单平台重试可能卡住，或重复提交

位置：`app/api/upload-post/retry/route.ts`（约 24 行）；`lib/upload-post-sync.ts` 的 `syncPendingStatuses()`。

重试创建的新 request_id 只存入 publications，轮询却只查询 uploads.request_id，可能仍轮询旧任务。重试先写入 retrying 再调用外部接口，但网络异常缺少恢复分支，导致一直处于 retrying，界面又只允许 failed 重试。另有并发点击时先查后改、缺少条件更新的竞态，可能提交两次。

建议：按 publications 的活动任务 ID 轮询；条件更新原子领取重试任务；外部响应未知时先对账，不直接再次发布。

### 3. P1：Webhook 先标记收到，再处理，失败后重试会被忽略

位置：`app/api/upload-post/webhook/route.ts`（约 27–34 行）。

delivery_id 在事务外先插入；后续状态更新失败时，这条 delivery 仍存在。平台重投相同 delivery_id 会直接返回 duplicate，状态变更可能永久丢失。

建议：幂等记录与业务更新同事务，或增加 processing / completed / failed 状态并允许未完成任务重试。

### 4. P2：外部接口拖住提交和审批页面

位置：`lib/notifications.ts`、`lib/upload-post.ts`、`app/api/upload-post/profile/route.ts`、提交/审批路由。

提交和审批会同步等待 Lark 通知；Lark fetch 未指定超时，每条消息又重新获取 tenant token。上传页连接检查使用通用 5 分钟超时。即使数据库操作已成功，页面仍可能一直等待外部服务。

建议：通知使用持久队列和独立投递；缓存 tenant token；连接检查采用较短超时和短时缓存。不要只用不受管理的后台 Promise，以免进程重启丢通知。

### 5. P2：多轮同步可以同时运行

位置：`app/api/upload-post/sync/route.ts`、`lib/upload-post-sync.ts`。

定时任务和任何已登录用户点击同步都可启动完整同步，没有整轮互斥。多个请求会重复调用外部 API、写快照、清理文件和发送维护通知。

建议：为整轮同步加数据库 advisory lock / job 状态，重复触发返回正在运行。本次只合并了看板预计算的并发，不改变整个同步业务流程。

### 6. P2：历史导入 UUID 生成可能冲突（已本地复现）

位置：`lib/records.ts` 的 `syntheticUuid()`（约 54 行）。

实现只是将 seed 转 hex 后截取前 32 个字符，等价于仅使用前 16 字节；同前缀、不同后缀的 request ID 会得到相同 UUID。已用两个不同 seed 验证碰撞。

建议：使用稳定哈希生成 UUID，并先对账已有记录，避免直接替换算法后生成重复导入。

### 7. P2：OAuth 返回路径校验不完整（已本地复现）

位置：`lib/auth.ts` 的 `safeReturnTo()`（约 72 行），以及登录页对应判断。

只检查以 / 开头且不是 //，没有排除反斜杠。浏览器 URL 解析可把一个斜杠加反斜杠开头的路径解释为其他域名，形成登录后的站外跳转。

建议：用 URL 解析后验证 origin 完全相同，再返回 pathname / search / hash；补充控制字符与反斜杠用例。

### 8. P2：清理失败仍把文件标记为已删除

位置：`lib/maintenance.ts` 的删除循环；`lib/upload-staging.ts` 的过期清理。

文件删除异常被吞掉，随后仍清空 media_path / 删除会话记录。权限或磁盘错误时，会产生无法通过数据库定位的遗留文件，计数也会显示删除成功。

建议：只忽略 ENOENT；其他错误保留路径和待重试状态，记录不含凭据的错误码。

### 9. P2：日期筛选存在请求竞态与统计口径混淆

位置：`app/dashboard/page.tsx` 的 load、`app/weekly-report/page.tsx` 的 Accounting load；`lib/dashboard-data.ts` 与 `lib/weekly-report-data.ts`。

快速切换时间范围时，旧请求晚返回可能覆盖新选择。当前看板主要汇总“范围内上传视频的当前累计指标”，不是“该时间段所有视频新增的指标”；日期控件部分按浏览器本地时区，而周报按新加坡时间。与平台后台对账时很容易比较了不同口径。

建议：请求取消或序号校验；明确区分上传日期筛选与指标发生日期，并统一显示时区。本次保持原统计语义以保证性能修改可验证。

### 10. P3：CSV 导入逐行写入，放大文件时会明显变慢

位置：`lib/libtv-accounting.ts` 的 `importLibTvCsv()`（约 99–118 行）。

最多允许 10,000 行，但每行独立 INSERT，形成最多 10,000 次数据库往返。目前 448 行规模不是 Dashboard 卡顿主因。

建议：分批多行 INSERT / COPY，再统一去重，继续保留现有重复文件与重叠记录规则。

### 11. P3：文档与实际归因规则不一致

README 仍描述 24 小时窗口及无播放增量时平均分配；当前代码实际采用约 96 小时窗口、历史最高订阅数增量，且零播放增量不分配。应更新文档，避免后续维护按旧规则理解。

## 测试服代码漂移

测试服在 GitHub 基准之外还有视频里程碑通知、标题处理、媒体可用性及周报等改动。此次构建保留这些现有文件，仅把性能修复叠加进去；没有用仓库快照直接覆盖服务器。建议后续把这些现有功能补回 Git，并明确每个环境的部署提交，避免再次遗漏功能。

审查范围：仓库 app / lib / components 业务源代码、API、数据库层、同步与维护任务、历史导入脚本、部署配置，以及相关页面交互。上述未修复问题主要为代码路径确认；除注明本地复现及性能回归外，未在真实平台触发重试、发布、通知或故障注入。
